1. SYSTEM OVERVIEW & KEY MANAGEMENT ARCHITECTURE (HASHICORP VAULT + HEDERA MPC)
================================================================================

OjasRaksha operates without any centralized database (PostgreSQL, MongoDB, MySQL) 
or vendor-locked cloud KMS (such as AWS KMS). All medical payloads, prescriptions, 
diagnostic reports, and claims are client-side AES-256-GCM encrypted before being 
pinned to Pinata IPFS. Cryptographic IPFS Content Identifiers (CIDs), access state, 
and audit logs are recorded immutably on Hedera Hashgraph Smart Contracts and 
Hedera Consensus Service (HCS).

Why AWS KMS Was Replaced:
  - AWS KMS introduces cloud vendor lock-in and a centralized point of failure.
  - Under India's DPDP Act 2023, data fiduciaries and principal patients must maintain 
    sovereign cryptographic control over key lifecycle without third-party cloud exposure.
  - AWS KMS pricing and centralized key escrow violate true Web3 zero-trust healthcare.

HashiCorp Vault + Hedera MPC Key Management Architecture:
  1. HashiCorp Vault (Transit Secrets Engine): Provides high-performance, self-hosted, 
     HSM-compatible transit encryption, key rotation, and zero-trust key isolation. 
     Vault handles envelope encryption enclaves without ever storing raw health records.
  2. Hedera Threshold MPC Key Vault: Web3 multi-party computation splits signing keys 
     across distributed nodes. Neither the application server, cloud provider, nor 
     hospital holds a complete key share.
  3. DPDP Key Shredding (Right to Erasure): When a patient revokes access or exercises 
     DPDP Right to Erasure, the Vault transit key version is revoked/shredded. The 
     IPFS payload remains encrypted forever with unrecoverable AES keys.

Key Smart Contracts:
  - DataFiduciaryRegistry.sol : Role governance & data fiduciary approvals
  - MedicalRecords.sol        : EMR CID anchoring, prescriptions & bill amounts
  - ConsentManager.sol        : Granular DPDP consent grants, scope & durations
  - AuditLog.sol              : Immutably logged data access & consent events
  - WalletMapper.sol          : Maps 42-char hex wallet addresses to 6-digit Short IDs
  - RBAC.sol                  : Role-based permissions (Doctor, Pharmacy, Lab, etc.)

Hedera HCS Topic ID: 0.0.4891024 (Real-time immutable audit mirror)

                   | + Hedera Merkle Batching Algo  |

Step-by-Step Flow:
  1. WEBSITE ENTRY & LANDING:
     - Patient opens the OjasRaksha platform portal.
     - System displays a zero-trust, modern Web3 healthcare interface.
  2. WALLET CONNECTION / CREATION:
     - Patient clicks "Connect Wallet" (MetaMask, HashPack) or "Create Health Wallet" 
       via Web3Auth Social Login (Google / Passkey / Email).
     - Web3Auth uses Threshold Multi-Party Computation (MPC) to generate key shares 
       without exposing private keys to central servers.
  3. DPDP CRYPTOGRAPHIC CHALLENGE SIGNATURE:
     - System generates a unique cryptographic nonce and timestamp challenge:
       "Sign to authenticate identity & grant DPDP 2023 Consent Manager access"
     - Patient signs challenge off-chain using their wallet private key.
     - Server verifies EC signature off-chain; zero password storage needed.
  4. SHORT ID RESOLUTION & ON-CHAIN REGISTRATION:
     - App queries `WalletMapper.sol` with patient's 42-char EVM address (e.g. 0x7099...).
     - If new patient, `WalletMapper.sol` executes `getOrCreateShortId()` to assign 
       a clean 6-digit Short ID (e.g. 849201) mapped permanently to the wallet.
  5. CLIENT-SIDE ENCRYPTION KEY SETUP (HASHICORP VAULT + DERIVATION):
     - Patient browser derives a master symmetric encryption key using PBKDF2/Argon2 
       from wallet signature seed.
     - Registers public key enclave handle with HashiCorp Vault Transit Engine for 
       secure transit envelope encryption.
  6. BASELINE HEALTH PROFILE & HISTORICAL EHR RECORD INGESTION:
     - Patient populates initial health profile (Blood Group, Allergies, Emergency Contacts).
     - Patient uploads previous paper/digital health records (scanned PDFs, diagnostic reports, 
       past discharge summaries, DICOM images).
     - AI/ICD-10 Engine parses legacy documents, extracts diagnosis codes, and structures 
       payload into HL7 FHIR R4 standard resources (`DocumentReference`, `Condition`).
     - Files are client-side AES-256-GCM encrypted and pinned to Pinata IPFS.
  7. HEDERA HASHGRAPH OPTIMIZATION ALGORITHMS:
     - Algorithm 1: HCS Merkle Tree Batching & CID Chunking Algorithm
       * When uploading N historical documents, client computes Merkle Tree root:
         Merkle Root = SHA256(CID_1 || CID_2 || ... || CID_N)
       * System submits 1 single Merkle Root commitment transaction to Hedera HCS 
         Topic 0.0.4891024 instead of N separate on-chain transactions.
       * Reduces Hedera transaction overhead by 90%+, achieving ultra-low cost ($0.0001) 
         and zero ledger congestion.
     - Algorithm 2: Gossip-about-Gossip Consensus Finality
       * Hedera's Asynchronous Byzantine Fault Tolerant (aBFT) virtual voting provides 
         100% deterministic finality in <3 seconds with zero proof-of-work latency.
     - Algorithm 3: ZK-HCS Hash Commitment & Integrity Proof
       * Off-chain ZK hash commitment algorithm verifies document authenticity:
         Commitment = PoseidonHash(RecordHash, PatientShortID, Nonce)
       * Enables providers to verify legacy document authenticity before consent grant.
  8. DPDP DEFAULT CONSENT POLICY SETUP:
     - Patient configures default privacy preferences (e.g. default consultation consent 
       expiry = 24 hours; Emergency Break-Glass opt-in = Active).
     - Preferences registered on `ConsentManager.sol`.
  9. DASHBOARD ROUTING:
     - System verifies `RBAC.sol` (Patient default role) and redirects user to `PatientDashboard.jsx`.

     - Platform Super Admin accesses `AdminDashboard.jsx` and verifies facility credentials.

         * Employee Wallet Address / 8-Digit Short ID

     - Hospital Admin signs transaction calling `RBAC.sol` (`registerRole(employeeWallet, roleId)`):
         * Role 1: Hospital Admin / Facility Operator

     - HashiCorp Vault Transit Engine issues a role-scoped cryptographic transit token.
     - Token permissions strictly restrict encryption/decryption privileges to the 
       employee's verified RBAC role and active patient consent grants.
  7. IMMUTABLE HCS AUDIT PROVENANCE LOGGING:
     - Event `EMPLOYEE_ROLE_GRANTED` containing (Facility Address, Employee Address, 
       Role ID, Professional Registration Hash, Timestamp) is published to Hedera 
       Consensus Service HCS Topic `0.0.4891024`.
  8. EMPLOYEE FIRST-LOGIN & DASHBOARD ROUTING:
     - Employee opens platform, connects wallet, and completes DPDP challenge signature.
     - App checks `RBAC.sol` contract; detects assigned role and routes employee directly 
       to their specific interface (`DoctorDashboard.jsx`, `PharmacyDashboard.jsx`,

     - Doctor enters Patient Short ID or Wallet Address in Doctor Dashboard.

     - Patient receives notification in `PatientDashboard.jsx`.

     - Encrypted ciphertext is uploaded to Pinata IPFS, returning IPFS Content ID (CID).

     - Doctor calls `addRecord(patientAddress, cid, recordType, billAmount)` on `MedicalRecords.sol`.
  6. AUDIT LOGGING:
     - Event is emitted on-chain (`DataAccessed` / `RecordAdded`) and mirror-logged to 
       Hedera Consensus Service HCS Topic `0.0.4891024`.
